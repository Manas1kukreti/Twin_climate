## Architectural Boundaries

### `src/`

Contains reusable research/application logic. Code needed by more than one notebook/script/dashboard component belongs here.

### `src/models/`

Contains model definitions only. Avoid embedding full experiment orchestration inside model classes.

### `scripts/`

Contains explicit executable entry points for data acquisition, preprocessing, training, evaluation, and figure generation.

Scripts should call reusable `src/` functions rather than duplicate implementation.

### `configs/`

Contains reproducible experiment configuration. Prefer configuration-driven experiments over editing constants in source files.

### `notebooks/`

Use notebooks for EDA, exploration, diagnostics, and review-friendly analysis. Do not make notebooks the sole location of production/research-critical preprocessing, evaluation, or model logic.

### `data/raw/`

Contains immutable or minimally altered source data. Never overwrite raw source data during preprocessing.

### `data/processed/`

Contains derived clean/split/sequence-ready data. Processed data must be reproducible from raw data plus configuration.

### `data/sample/`

Contains only small representative data needed for fast tests or examples. Never treat sample data as final experiment data unless explicitly intended.

### `data/metadata/`

Stores dataset metadata such as source, retrieval parameters, variable definitions, units, geographic bounds, sampling interval, and preprocessing summaries.

### `results/checkpoints/`

Stores model checkpoints. A checkpoint should be associated with a run manifest.

### `results/metrics/`

Stores machine-readable metrics generated by evaluation code.

### `results/manifests/`

Stores experiment provenance. Each meaningful run should have a manifest linking configuration, dataset/split, seed, model, checkpoint, and outputs.

### `results/figures/`

Contains figures generated from saved experimental outputs. Figures should be reproducible via scripts.

### `dashboard/`

Contains presentation and interaction code. The dashboard must consume research artifacts rather than reimplement training/evaluation logic.

### `tests/`

Contains fast, deterministic tests where possible. Prioritize tests for data leakage, temporal alignment, tensor shapes, autoregressive update logic, metric correctness, and artifact loading.

## Dependency Direction

Prefer this direction:

```text
configs/data
    ↓
src reusable logic
    ↓
scripts / notebooks / dashboard
    ↓
results
```

The dashboard should depend on `src/` and saved `results/`, not the other way around.

Avoid circular dependencies between models, training, forecasting, and dashboard code.

## Naming Conventions

Use clear names that encode scientific meaning.

Prefer:

- `train_df`, `val_df`, `test_df`;
- `input_window`, `forecast_horizon`;
- `feature_names`, `target_names`;
- `sampling_interval_hours` when the unit is actually hours;
- `y_true`, `y_pred` for evaluation arrays;
- `checkpoint_path`, `metrics_path`, `manifest_path`.

Avoid generic names such as `data1`, `temp2`, `final_model_new`, or `results_latest` for persistent artifacts.

## Artifact Naming

Use stable run IDs, for example:

```text
transformer_scratch_delhi_seed42_001
transformer_pretrain_india_seed42_001
transformer_finetune_delhi_seed42_001
```

A run ID should be usable to connect:

```text
configuration
→ manifest
→ checkpoint
→ metrics
→ figures
```

## Git Hygiene

Keep generated caches, virtual environments, large raw data, large model checkpoints, secrets, and local credentials out of version control.

Never commit API keys, `.env` secrets, `.cdsapirc`, private credentials, or authentication tokens.
